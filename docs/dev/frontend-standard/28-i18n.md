## In this project

- Paraglide JS ([ADR 0012](../adr/0012-infrastructure-libraries.md)) in `web/packages/i18n`: one message file for the dashboard and the site, `messages/ru.json`. Russian is the base locale and the only locale for now.
- `pnpm install` (`postinstall`) and `mise run gen` compile the messages into typed functions in `src/paraglide`. Paraglide marks that folder as generated and git ignores it. An app imports `m` from `@app/i18n` and calls `m.key()`, so a missing key is a type error, and the site sends no JavaScript for it.
- Plural forms use the `plural` selector with `Intl.PluralRules`: Russian needs `one`, `few` and `many` (see `photos_count`). A test checks the forms.
- The message-format plugin loads from jsdelivr with a pinned version: Paraglide does not read a local plugin path (it compiled zero messages, and the tests caught it).
- No UI text in components: add a key to `messages/ru.json`. Key names: `<area>_<thing>`, snake case.

## Collected points

### Native-platform i18n instead of an i18n framework

Source: [Building a Lightning-Fast i18n Alternative](https://dev.to/artalar/building-a-lightning-fast-i18n-alternative-why-i-ditched-i18next-for-native-javascript-2o06) (Artyom / @artalar_dev).

**Why not i18next at scale:** ~1 s of TS compilation per 1 000 keys, IDE lag on large dictionaries, 13.2 kB gzip runtime before any translations, custom-DSL parsing at runtime; reports of CI memory overflow at ~3 k keys and 3× SSR gains after removal. (Resonates with D11 — tooling latency is a first-class concern.)

**The native approach:**

- **`Intl.*` does the formatting** — `NumberFormat` (numbers/currency/units), `DateTimeFormat`, `PluralRules` (pluralization), `RelativeTimeFormat`; no DSL reimplementation of what the browser ships.
- **Translations are typed TypeScript modules**, one per language — full type inference, dot-notation access (`t.key`), compile-time missing-key safety.
- **Only the active language loads** — dynamic import per locale gives code-splitting for free.
- **Computed translations are plain functions** using the native formatters.
- Locale persistence via a simple cookie; SSR-compatible without special setup; framework-agnostic.

**Trade-off:** translations living in code are hard for non-technical editors — mitigations: build-time generation from an external source, Git-based workflows, or a hybrid.

Open question for elaboration: whether the standard defaults to this native approach or only mandates its principles (typed keys, per-locale splitting, `Intl` for all formatting) while leaving the mechanism open per project.
